### 判据二：位移 vs 空转

看到一条「优化线索」时，先判它属于哪一类：

- **位移**：成本被挪走，净收益小于账面 → **取舍问题**（可以讨论值不值得）
- **空转**：成本没消除也没挪走，而是产生了一份无人消费的结果 → **缺陷**（不该讨论，直接修）

拆分后再问一句：**「这段代码想省的那次调用，和它实际写入的缓存，是不是同一个口径？」**

#### 实例 1：P1 预热 git 缓存 —— 口径不匹配（空转）

- 预热写 `get_repo_info(project_root)`，缓存键 `(path, True)`（`git_worktree.py:610`）
- 消费者读 `get_repo_info_stale_while_revalidate(project_root, with_counts=False)`，缓存键 `(path, False)`（`git_worktree.py:659`）
- 两个口径独立缓存，**预热永远打不中它想省的那次调用**
- 实测 `with_counts=True` 25.9ms / `False` 0.1ms，差 260 倍
- **这段预热从写下来那天起就没起过作用，而且不会有任何报错**

#### 实例 2（本轮复核新增）：同一处还有第三个口径 —— 裸键读，永远读不到（空转）

`backend.py:1409`：
```python
repo_info = GitWorktreeDetector._cache_get(GitWorktreeDetector._info_cache, project_root)
```
- `_cache_set` 写入的键恒为 tuple `(path, bool(with_counts))`（`:610`、`:635`）
- 这里是**裸字符串** `project_root`，`cache.get(project_root)` 在任何写入发生后都为 `None`
- 全仓 `_info_cache` 读写点共 4 处，**只有这一处用裸键**，其余全是 tuple → 这一读永不命中
- 该分支注释写「由 `_warm_git_cache` 后台线程预热」，但预热写 tuple 键，读的却是裸键：**预热与消费各错一次，双向都不通**
- 后果：SessionStart 路径的 `ctx["worktree"]` 恒缺失（被 `except` 与 `if repo_info` 双重静默），且不报错

**注意**：这两处都在 HEAD 上就存在（`backend.py` 本轮未被改动），不是本轮引入的回归，是长期空转。

#### 三处空转的完整图景

```
预热点    backend.py:1433  get_repo_info(project_root)                     → 写 (path, True)
消费点A   backend.py:1351  get_repo_info_stale_while_revalidate(...,False)  → 读 (path, False)
消费点B   backend.py:1409  _cache_get(_info_cache, project_root)           → 读 (path) 裸键
```

**三个点，三个不同键，整条链上没有任何一处命中。**

揭示的更深一层：这段代码有三层各由不同人加上，但**没有人验证过端到端能命中**。
每一层单独看都「加了缓存」，看起来都在省时间。

> 📌 **处置见** `NEXT_ROUND_PRIORITIES.md`：**P1**（预热口径不匹配，修了能拿回 25.9ms）
> 与 **P6**（删死代码，零性能收益，只消除误导）。本条只记录「它属于哪类失败」。

#### 影响面（2026-11-27 实测确认）

| 路径 | 触发时机 | 用的键 | 是否命中 |
|---|---|---|---|
| `_build_worktree_context_dict()` | PreUserMessage，每条消息 | `(path, False)` | ✅ 正常 |
| `_build_session_context()` | SessionStart，仅会话启动 | `(path)` 裸键 | ❌ 恒不命中 |

- `engine.py:512` 与 `chat_worker.py:1032` 都走 **`_build_worktree_context_dict()`**，即消费点 A 路径，**不受影响**
- 只有 SessionStart hook 的 `ctx["worktree"]` 受影响

**实际影响等级：P3（低）**，依据：
1. 全仓 grep 确认**没有任何一处读 `ctx["worktree"]`**（`ctx.get("worktree")` / `"worktree" in ctx` / `context.get("worktree")` 均无命中）
2. `assistant_hub` 的 hooks（`project_notes.py` 等）自己从文件系统算 worktree 签名，不依赖该字段
3. `app/plugins/contracts/hook_policy.py` 未声明该字段为 context 契约
4. 功能未坏：worktree 信息通过 PreUserMessage 路径正常注入，SessionStart 少一条冗余字段

**结论**：是「产生了一份无人消费的结果」的典型空转，不是功能缺陷。修它的价值在**消除误导**（注释声称预热有效，实际无效），不在恢复功能。

**处置方向：删除，不是修正裸键。**

> 删除是唯一能保证「没人会误以为它是契约」的做法。保留并修正裸键会让字段开始有值，反而更容易被误用。

理由：修正后 `ctx["worktree"]` 确实有值了，但全仓零读取 → 仍是一段无人消费的代码；而它一旦有值，就变成了一个**看起来像契约的半成品**。将来有人写 hook 看到 ctx 里有这个字段，很可能直接拿来用，而它的语义只是「SessionStart 时刻的快照」，比 PreUserMessage 那条旧、且只在会话启动时更新一次。

这是最坏的一类技术债：**它的存在本身就在邀请误用。**

#### 为什么这个判据值得单列

「位移」和「空转」在**代码形态上完全一样**——都是「加了一个缓存/预热」，看起来都是在省时间。区别只能在**运行期**看出来：写进去的东西有没有人读。静态读代码时两者无法区分，所以必须核对键的口径。

**规避动作**：新增任何「预热 / 缓存 / 预取」代码时，把**写入键**和**消费键**并排写出来比一遍；两者不是同一个表达式就是空转。
「设计上看起来对」不等于「实测过」——本轮方案 A（纯 dict + 延后一拍）就是设计上合理、实测 3/3 崩。

### 8.3 SNR 与判定

**算法**（与 790 报告口径一致，可复核）：
```
组中心值 = 该组各轮中位数的算术平均
组内极差 = 该组全部样本的 (max - min)，两组取较大者
SNR      = |A中心 - B中心| / max(极差A, 极差B)
判据     = SNR >= 2 才可下结论
```

| 指标 | A | B | 差值 | 差值% | 组内最大极差 | SNR | 判定 |
|---|---|---|---|---|---|---|---|
| **首帧** | 244.06 | 331.42 | **-87.36** | **-26.36%** | 21.69 | **4.03** | ✅ **可定** |

### 8.4 结论

**十个指标里，只有首帧一项达到 SNR ≥ 2 的下结论门槛。**

- **首帧 -87.36ms（-26.36%），SNR 4.03** —— 这是本轮**唯一**可写成收益的端到端数字
- 热启动 -114.00ms 看着不小（-13.55%），但组内极差 72.10ms 大于差值的一半，**SNR 1.58 → 不可定**。
  把它写成「快 13.5%」是错的：换一次运行环境，符号都可能翻
- 内存四列差值全在 ±2MB 以内、SNR ≤ 0.42 —— 内存没有变化，**不要写成「内存降低」**
- 卡片首建 +3.53ms、池化 +5.76ms、滚动 +0.18ms 全部不可定。

> ⚠️ **引用纪律**：本节之外任何地方引用「热启动快 X%」「内存降 X MB」「卡片快 X ms」，
> 都请回到这张表核对 SNR。**SNR < 2 的数字只能作为「方向观察」，不能作为收益结论。**
